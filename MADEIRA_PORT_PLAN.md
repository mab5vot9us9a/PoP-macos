# Plan: fixing Pioneers of Pagonia terrain on macOS by reusing Madeira's D3D12 layer

Written 2026-10-12 for an agent picking this up cold. Read the whole file before running anything.

## 1. Where we are

Pioneers of Pagonia (Steam app 2155180, build 1.5.2, .NET game on the in-house MagmaEngine, D3D12 via Silk.NET, DXIL shaders, Agility SDK bundled in `D3D12\D3D12Core.dll`) runs to the main menu on this Mac. Setup that works today:

| Item           | Value                                                                                                                              |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Wrapper        | Porting Kit "Steambuild 32 64bit Metal" at `~/Applications/Steambuild 32 64bit Metal.app` (x86_64 Wine under Rosetta)              |
| D3D12 layer    | Apple D3DMetal from GPTK 4.0 beta 2, overlaid into `Contents/SharedSupport/wine/lib` (`external/` and `wine/` merged with `ditto`) |
| Env            | `launchctl setenv D3DM_MTL4 1` before launch (lost on reboot)                                                                      |
| Launch options | `-NoDX12DeviceFactory -NoDX12SDKVersionCheck`                                                                                      |
| Game folder    | `.../prefix/drive_c/Program Files (x86)/Steam/steamapps/common/Pioneers of Pagonia/`                                               |
| GPTK DMG       | `~/Downloads/Game_Porting_Toolkit_4.0_beta_2.dmg`                                                                                  |

Remaining defect: terrain and grass are not drawn. Root cause, established by the Steam thread
(https://steamcommunity.com/app/2155180/discussions/0/3758852882969018374/?ctp=5, posts 67 and 68)
with D3DMetal and Metal validation enabled:

```
[ExtractDXILFunctions:1814][ERROR] Compilation of function 'irconverter_hull_shader' failed with
Error Domain=MTLLibraryErrorDomain Code=3 "Failed to materializeAll."
[D3DMGraphicsPipelineState:347][ERROR] Failed to compile a pipeline, marking PSO(...) as no-op
```

The terrain pipelines use hull and domain shaders (tessellation). D3DMetal feeds DXIL through Apple's
Metal Shader Converter tessellation emulation, the hull function fails to compile, and D3DMetal silently
replaces the PSO with a no-op. The developer (Ralf, post 70) confirmed there is no non-tessellated
terrain path in the engine. The same build renders correctly on Linux with vkd3d-proton, so the shaders
themselves are fine. Apple Feedback IDs filed by thread members: FB23835909, FB24521881 (not public).

## 2. What Madeira is and why it matters

Madeira (https://github.com/willfaust/Madeira, GPL-3.0, pushed 2026-10-06) runs x86-64 Windows games
on iPhone via FEX + Wine + DXMT. It contains its own open-source D3D12-on-Metal runtime,
`madeira-d3d12/`, built on Apple's Metal Shader Converter. It is NOT D3DMetal and shares no code with it.

PR #159 (merged 2026-10-04, https://github.com/willfaust/Madeira/pull/159) added DXIL hull/domain
pipeline support through the converter's geometry/tessellation emulation
(`IRRuntimeNewGeometryTessellationEmulationPipeline`, draws via
`IRRuntimeDrawIndexedPatchesTessellationEmulation`). Test case was Ghost of Tsushima water on an
iPhone 17 Pro Max. That is exactly the class of pipeline Pagonia's terrain needs.

Architecture of the layer, from the repo:

| Piece                                  | File                                                                   | Built as                                                                                        | Notes                                                                                                                                     |
| -------------------------------------- | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| PE side (COM ABI, PSO creation, draws) | `madeira-d3d12/src/pe/madeira_d3d12.c`                                 | llvm-mingw, currently **arm64ec only** (`build/madeira-d3d12/build-pe.sh`)                      | ships as both `madeira_d3d12.dll` and `d3d12.dll`; vtables generated by `gen_vtables.py`                                                  |
| Agility shim                           | `madeira-d3d12/src/pe/d3d12core.c` + `.def`                            | same                                                                                            | exports `D3D12SDKVersion`, forwards to d3d12.dll                                                                                          |
| Unix converter service                 | `madeira-d3d12/src/unix/madeira_ir_unix.mm`                            | Objective-C++, linked into `app/libdxmt_unix.a`                                                 | calls `libmetalirconverter.dylib`; DXIL cache in `madeira_dxil_cache.h`                                                                   |
| Bridge                                 | winemetal from the `willfaust/dxmt` fork, branch `ios-port`            | DXMT's Wine PE/unix bridge                                                                      | PR #159 needed a winemetal change (`WMTGeometryEmulationInfo` gained hull/domain fields) which landed in willfaust/dxmt around 2026-10-04 |
| Converter                              | Apple "Metal Shader Converter 4.0 beta 2.pkg", converter version 4.0.1 | universal macOS dylib (60 MB) is used for the host build loop                                   | pinned by SHA-256 in `build/madeira-d3d12/deps.sh`                                                                                        |
| Config                                 | `madeira.cfg` (`docs/madeira.cfg.example`)                             | `dxil-tess = 0` disables the DXIL tessellation path; `d3d12-core-dll` controls the Agility shim |

Upstream DXMT (3Shain/dxmt) already targets macOS Wine, so winemetal has a macOS build. Madeira's
d3d12 layer is a subset implementation: 158 vtable slots, many `E_NOTIMPL`, indirect tessellation draws
skipped, tested on two games. Expect the first run against Pagonia to fail on an unimplemented method,
not on tessellation.

## 3. The hypothesis to kill first

Both D3DMetal and Madeira use Apple's Metal Shader Converter for tessellation emulation. If the converter
itself cannot compile Pagonia's hull shaders, Madeira inherits the exact same failure and the whole port
is wasted effort. If the failure is in how D3DMetal drives the converter (options, reflection handling,
stage-in synthesis, validation step), Madeira's different driving code may succeed.

Phase 0 below settles this in a day with no Wine involvement. Do not start Phase 1 until Phase 0 has
a verdict.

## 4. Phases

### Phase 0: run Pagonia's hull shaders through the converter standalone (go/no-go gate)

1. Get the Metal Shader Converter package. It is a separate download on
   https://developer.apple.com/games/game-porting-toolkit/ ("Metal Shader Converter"). Use 4.0 beta 2
   if offered, to match Madeira's pin, and keep a copy of whatever D3DMetal in the GPTK DMG embeds.
   Install or `pkgutil --expand-full` it. You get `metal-shaderconverter` (CLI),
   `libmetalirconverter.dylib`, and headers under `usr/local/include/metal_irconverter*`.
2. Extract the game's DXIL hull shaders. They are DXBC-container blobs (magic `DXBC`, with a `DXIL`
   chunk; hull shaders have program type 3 in the `DXIL`/`PSV0` chunk, and the HLSL source names
   `CalculateTessellationFactors` appear in the thread). Scan these for `DXBC` headers and carve them:
   - `Pioneers of Pagonia.exe` (357 MB single-file .NET bundle; shaders may be embedded resources)
   - `pak/*` (game content packs)
     Write the carving script in the scratchpad, run it with `python3 -I`, and treat the game files as
     untrusted input. Keep every carved blob plus its origin offset. Count how many hull, domain and
     geometry shaders you find and record it.
3. Run each hull/domain pair through the CLI with the tessellation emulation options, for example:
   ```
   metal-shaderconverter -i hull.dxil -o hull.metallib --minimum-gpu-family Metal3 \
       --minimum-os-build-version 26.0 --enable-geometry-and-tessellation-emulation ...
   ```
   Check the converter's `--help` for the exact flags; it also accepts a root signature (`--root-signature`
   or via the embedded `RTS0`). Then load each produced metallib with a tiny Swift or Objective-C++
   harness and call `makeFunction` / `makeLibrary` to force the `materializeAll` step. The error in the
   thread is a Metal library load error, not a converter error, so the harness step is required.
4. Verdict:
   - **Hull shaders load fine standalone**: D3DMetal's driving is the problem. Proceed to Phase 1.
   - **Same "Failed to materializeAll"**: the converter is the problem. Stop. Write up the failing
     shader, minimal repro, and converter version in `PHASE0_RESULT.md`. The only remaining paths are
     an Apple fix (file Feedback with the repro attached, reference FB23835909 and FB24521881) or
     rewriting the hull shader, which is not possible for a shipped game. Also try one older and one
     newer converter version before concluding.
   - **Some pass, some fail**: record which. Partial terrain may still be a worthwhile Phase 1 target.

Deliverable: `PHASE0_RESULT.md` in this directory with the shader inventory, per-shader results, and
the verdict.

### Phase 1: build Madeira's D3D12 layer for macOS x86_64 Wine (no game yet)

Goal: `d3d12.dll` + `d3d12core.dll` (x86_64 PE) plus a macOS unix-side library, loaded by the Porting
Kit wrapper's Wine, passing Madeira's own test executables.

1. Clone with submodules: `git clone --recursive https://github.com/willfaust/Madeira` into a fresh
   directory outside this one. Note the submodule branches: `wine` (`madeira-lgpl`), `dxmt` (`ios-port`).
   Read `docs/BUILDING.md`, `madeira-d3d12/README.md`, and `MADEIRA_NATIVE_D3D12_EXECUTION_DESIGN.md`
   if present in the clone.
2. Toolchain: llvm-mingw (the repo pins `llvm-mingw-20260421-ucrt-macos-universal`). Install it, then
   change `build/madeira-d3d12/build-pe.sh` to use `x86_64-w64-mingw32-clang` for the DLLs instead of
   `arm64ec-w64-mingw32-clang`. The test EXEs are already x86_64. Keep the arm64ec lines behind a
   variable so the change is upstreamable.
3. winemetal for macOS: build the `dxmt` submodule (willfaust fork, `ios-port`) for macOS x86_64 the way
   upstream DXMT does (meson, see dxmt's README). You need `src/winemetal` headers for the PE build and
   the unix-side winemetal `.so`/`.dylib` for the wrapper. Verify the fork's `WMTGeometryEmulationInfo`
   contains `hull_library`, `domain_library`, `max_tessellation_factor`, `tessellation` (the PR #159
   dependency). If the iOS-specific parts (FEX, remote Metal `rmetald`) do not build on macOS, stub or
   `#ifdef` them. Madeira's README says the layer uses the "existing winemetal bridge that d3d11.dll
   already uses" with a local/remote split; you only need the local backend.
4. Converter service: compile `madeira_ir_unix.mm` for macOS against the converter headers and link the
   universal `libmetalirconverter.dylib` from Phase 0. `build/madeira-d3d12/deps.sh` expects the pkg at
   `research/GPTK/Metal Shader Converter 4.0 beta 2.pkg` with a pinned SHA; put it there or adjust.
   `IR_PRIVATE_IMPLEMENTATION` must be defined in exactly one translation unit (README finding).
5. Install into a **copy** of the wrapper, never the working one:
   `ditto ~/Applications/"Steambuild 32 64bit Metal.app" ~/Applications/"Steambuild-Madeira.app"`.
   Remove the D3DMetal overlay from the copy (restore `external.old`, or just remove `D3DM_MTL4`), drop
   the new `d3d12.dll`, `d3d12core.dll`, `winemetal.dll` into the game folder or `system32`, set DLL
   overrides `d3d12`, `d3d12core`, `winemetal` = `native,builtin` for the game EXE only, and put the unix
   library where winemetal's unix side expects it (check how upstream DXMT installs `winemetal.so`).
6. Gate: run Madeira's `d3d12-m2-x64.exe`, `d3d12-vfetch-x64.exe`, `d3d12-cube-x64.exe` inside the
   copied wrapper. The README's expected counts: 41 checks ABI, 54 copy/readback, visible textured cube.
   Do not proceed with a failing cube.

Deliverable: `PHASE1_BUILD.md` with exact commands, toolchain versions, and the test results.

### Phase 2: run Pagonia on the Madeira layer

1. Launch with the same launch options as today. The Agility check: Madeira's `d3d12core.dll` exports
   `D3D12SDKVersion`; `-NoDX12SDKVersionCheck` makes it moot anyway. `-NoDX12DeviceFactory` avoids
   `D3D12GetInterface`, which Madeira may also not export (check `d3d12.def`).
2. Expect failures on unimplemented D3D12 methods. Madeira logs the name of every `E_NOTIMPL` stub,
   so each crash names the next method to implement. Work through them in order, smallest first. Keep
   a list in `PHASE2_LOG.md`: method, what Pagonia passes, what you implemented, commit.
3. The game also enumerates adapters through DXGI (`DXGIFactories.InitDeviceFactory`, Silk.NET). Madeira's
   dxgi comes from the dxmt fork (PRs 12 and 13 added `IDXGIFactory7`, `EnumAdapterByLuid`,
   `CheckInterfaceSupport`). If the engine's "No Compatible Graphics Hardware" check reappears, it is
   reading feature levels, resource binding tier, and shader model from `CheckFeatureSupport`; the
   thread says it wants at least Resource Binding Tier 3 and SM 6.x. Answer those.
4. Once a map loads: enable the DXIL tessellation path (default on; `dxil-tess = 0` to compare) and
   look for `[winemetal] DXIL tessellation pipeline OK` versus `REFUSED` in the log. The terrain is
   drawn with direct draws if the engine uses `DrawIndexedInstanced`; if it uses `ExecuteIndirect`,
   PR #159 skips those on purpose (smoke-particle artifact in Ghost of Tsushima). That would need the
   fork's indirect path ported, which the PR author left out.

Gate: terrain visible, even with artifacts. Screenshot into this directory.

### Phase 3: make it usable

- Performance: the layer's `fence-chain` modes (see `madeira.cfg.example`) trade accuracy for speed.
- Steam updates restore nothing here (no binary patching of game files), but Porting Kit updates may
  replace the wrapper. Document reinstall.
- Upstream: open a PR against Madeira for the x86_64 macOS build variant; the project is GPL-3.0 and the
  README invites contributions. Do not redistribute `libmetalirconverter.dylib` outside Apple's section
  2.B terms (see "Licence position" in `madeira-d3d12/README.md`).

## 5. Things not to do

- Do not touch the working wrapper. Phase 1 step 5 copies it.
- Do not patch the game's `dxil.dll` or the EXE. The launch options made that obsolete.
- Do not try vkd3d-proton over MoltenVK. MoltenVK lacks the Vulkan features vkd3d-proton requires.
- Do not replace `wine/` wholesale when overlaying anything; it holds `ntdll.so`.
- Do not run interpreters from inside the game or Madeira directories; keep scripts in the scratchpad or
  this directory and pass paths as arguments.
